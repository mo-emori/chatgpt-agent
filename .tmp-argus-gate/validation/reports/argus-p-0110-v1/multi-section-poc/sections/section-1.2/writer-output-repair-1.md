## 1.2 Overall Structure

### Human Structure Plan

This section first establishes why the design must be presented as one connected structure, then names the operational domains covered by that structure, and finally explains each premise-to-protection chain. A rationale table is the primary representation because the essential content is a set of parallel causal relationships. The table preserves, for every relationship, the premise or failure mode, its consequence, the governing policy, the implementing mechanisms, and the protected concern. A separate closing paragraph explains how these relationships form a closed loop. No diagram is required: the supplied context identifies a component or sequence diagram only as a review candidate and does not define enough relationships to construct one without invention.

### Purpose and scope

When objectives, assumptions, processes, and safeguards are scattered, it becomes difficult to trace the causality and closed loops of the design as a whole. A list of adopted mechanisms is not sufficient, because downstream work cannot determine which assumption or failure each mechanism is intended to address. This section therefore presents the relationship from purpose to means, and the connections among the core processes, as one structure. It preserves the causal chain among each problem, its reason, the governing policy, the implementation mechanism, and the asset or condition being protected.

The overall structure covers Human-in-the-loop operation, the closed loop of investment decisions, Local-first operation, state preservation, validation, and improvement. Within that scope it connects Runtime, API, Writer, Risk, Approval, Fact, notification, Backup, Data, Cost, Storage, Break, and Validation concerns.

### Causal structure of the safeguards

| Premise or failure mode | Consequence | Governing policy | Implementing mechanisms | Protected concern |
|---|---|---|---|---|
| A PC is not continuously running or online. | Schedules can be missed, processing can be interrupted, and decisions can become stale. | Treat shutdown, sleep, and offline periods as normal operating conditions. | Loop processing, `last_success`, Retry, Durable Stage, and Catch-up. | Prevent permanent job loss, duplicate charges, and stale Proposals. |
| Side effects performed through an external API cannot be rolled back locally. | API cost or external processing can diverge from the State Commit. | Separate the Stage boundary from the Commit boundary. | `request_id`, hash binding, idempotency, and Stage reuse. | Prevent duplicate Calls and duplicate application to State. |
| Multiple Writers can corrupt the canonical JSON. | Version conflicts, partial writes, and duplicate resource allocation can occur. | Use a Single Writer with Atomic Commit. | OS lock, reread, version check, `fsync`, and atomic replace. | Protect Canonical integrity, Cash, and reservation. |
| Investment-attractiveness judgment and Hard Risk evaluation are handled by the same LLM. | The system could bypass Policy or produce a false PASS. | Separate a deterministic Validator from the LLM judgment. | Fixed code, hash binding, and CV-16A / B. | Protect funds and Risk Policy. |
| Approval and resource allocation occur in separate Commits. | The same Cash or Position can be assigned to multiple Trades. | Commit Approval and the Slot / reservation together. | Serialize the first item and apply it through the Writer. | Prevent double allocation. |
| Paste ingestion is made dependent on Proposal validity. | A real execution could disappear after TTL expiry or a Policy change. | Separate Fact ingress from Proposal evaluation. | Inbox, Fact Event, and Compliance Record. | Keep Broker reality consistent with the Portfolio. |
| BUSY is implemented only as notification suppression. | The system can forget to clear the condition, leaving a sticky BUSY state and a Queue that remains pending for a long period. | Use a time-limited Lease and return to NORMAL. | Presets, `effective_until`, and StatusLeaseJob. | Prevent Human availability from being fixed incorrectly. |
| Popup success is treated as Human awareness. | The system can incorrectly conclude that an incident has been handled. | Separate Delivery from ACK. | Durable Alert Queue and alert ack. | Prevent incidents from being missed. |
| A Backup restore cannot roll back Broker reality. | Restored State can diverge from the actual account. | Require Reconciliation after Restore. | Stop BUY / ADD and process missing Fact / Correction. | Prevent unsafe resumption of operation. |
| Historical Data can be revised later and can contain survivor bias. | Backtest performance can be overstated. | Require PIT handling, revision information, vintage information, and the Universe as it existed at the time. | Time Gate and Dataset Manifest. | Prevent look-ahead bias. |
| Future knowledge learned by an LLM cannot be blocked. | Replay could be misrepresented as genuine OOS evaluation. | Separate Quant Replay from Model Replay and display the limitation. | Connect the evaluation to prospective Paper operation. | Prevent unjustified performance claims. |
| An automatic Paid fallback is used during a cost-related failure. | It can create unauthorized charges and additional dependencies. | Make Paid Governance a Hard Rule. | `approval_ref`, Registry, and Budget Gate. | Protect cost authority. |
| Storage exhaustion causes features to fail in an accidental order. | State or monitoring can fail before Raw Data does. | Define an explicit degradation order. | Stop first / Preserve last and Minimum Data. | Protect Canonical data, Audit data, and Position Watch. |
| A Break can change evaluation criteria opportunistically. | Deteriorating performance can be concealed by changing the evaluation. | Strongly protect B4. | Freeze the old Objective, run old and new Objectives in parallel, and require two-stage Human Approval. | Preserve consistency of evaluation. |
| Test criteria can be adjusted to match implementation results. | A false PASS can be produced. | Freeze the baseline / oracle before the Run. | Hash the frozen material, place it in a separate Commit, and require Human Approval. | Protect Validation Integrity. |

Together, these chains define the overall closed-loop structure. Runtime continuity and staged external work protect execution across interruption; the Writer and atomic state transition protect canonical resources; deterministic Risk checks and coupled Approval protect decisions before commitment; Fact ingress and Reconciliation preserve Broker reality; notification leases and acknowledgements preserve Human participation; historical-data controls, replay separation, protected objectives, and frozen test criteria preserve the meaning of evidence; and cost and storage controls preserve the authority and operating substrate on which the loop depends.
