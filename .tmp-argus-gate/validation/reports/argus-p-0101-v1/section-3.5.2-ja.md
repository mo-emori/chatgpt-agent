## 3.5.2 Application Log

Application Log は、Runtime、Job、Adapter、Error、およびこれらに類する活動について、運用分析および障害分析を行うための記録である。これは Canonical State、Fact、Event、および Audit Record とは別個のアーティファクトである。このアーティファクト境界の設計上の参照先は、§2.6、§4、および §28 である。これは `logs/application/YYYY-MM-DD/` 配下に保存される。これを生成するコンポーネントおよび Writer の実装は、まだ決定されていない。

Application Log は、Canonical State、Fact、Event、または Audit Record の代替となってはならない。Application Log を削除しても、投資判断、状態、履歴を含む、正本となる設計情報が失われてはならない。したがって、その保存優先度は Canonical State、Commit、および Audit より低く、保持には有限の上限がある。具体的な保持期間は未解決のままである。

### ローテーションおよび日付単位の管理

Application Log は、`Asia/Tokyo` の日付境界で日次ローテーションしなければならない。このローテーションにより、ログを日付単位で管理可能にしなければならない。

### 記録してはならない情報

Application Log は、以下のいずれも記録してはならない。

- Secret
- Credential
- Token
- API key
- Authorization header
- 未編集のデバッグダンプ

これら既知の禁止項目以外で、禁止またはマスキングのいずれかを行わなければならない情報の範囲は、未解決のままである。

### 書き込み失敗の分離およびストレージの安全性

Application Log の書き込みだけに影響する失敗によって、Canonical Commit または正本となる投資処理が失敗してはならない。そのような分離された書き込み失敗は、可能な範囲で観測可能にしなければならない。

この分離は、正本の安全性に優先するものではない。同一のストレージ障害によって正本の安全性が損なわれる場合は、Storage Fail Closed が適用される。

### 環境の分離

Application Log は、TEST / PAPER / LIVE 間の Runtime Identity に基づく分離に従わなければならない。また、Development と Runtime の物理的な分離にも従わなければならない。これらの分離された環境またはドメインに属するログを、互いに混在させてはならない。

TEST / PAPER / LIVE を分離し、かつ Development / Runtime を分離する具体的なパーティション方式またはパス方式は、未解決のままである。

### 未解決の実装上の選択肢

以下の事項は未解決のままであり、固定された実装要件として扱ってはならない。

- 生成コンポーネント、Writer の責務、および書き込みパス
- 具体的な保持期間、およびクリーンアップまたは削除を実行するために使用する方法
- クラッシュ直前におけるログの耐久性保証の範囲
- Runtime、Job、Adapter、および Error のそれぞれについての最小限の識別情報
- 環境およびドメイン分離のための具体的なパーティション方式またはパス方式
- 既知の禁止項目に加えて、禁止またはマスキングの対象としなければならない情報
- ファイル名、ファイル形式、スキーマ、およびロギングライブラリ
